FF7 Accessibility Mod — TODO / Minor Issues
============================================

These are low-priority items identified during development. Not bugs blocking
current functionality; noted here for a future cleanup pass.


[TTS] Controller-button Unicode glyphs in dialog text
------------------------------------------------------
Some field dialogs contain characters like 0xD6 (Û) and 0xD9 (Ù) in FF7's
custom encoding. These map to controller button icons (e.g., Cancel button,
Direction pad) rather than alphabetic characters. Example dialog:

  "Run by holding [CANCEL] while using the [DIRECTION] buttons."

FF7's font renderer draws the appropriate button sprite; TTS sees a raw
Unicode code point with no meaning. Currently spoken as garbage or silence.

Fix ideas:
  - In ff7_text.cpp's decode table, map these code points to short descriptive
    strings (e.g., 0xD6 -> L"[Cancel]", 0xD9 -> L"[Dpad]").
  - Cross-reference the FF7 font/glyph table to identify all such mappings.
  - May also apply to other high-range characters in the custom encoding.


[TTS] "New Game" spoken during company logo splash (~350ms after launch)
------------------------------------------------------------------------
TITLE_CURSOR (0x00DD6F24) is in BSS and is zero-initialized before the title
screen module runs. TitleCursorThread's first poll fires at ~350ms while
Eidos/Square Enix logos play; it reads 0 (= New Game) and announces it.

The FIELD_ID gate (added in v1.9.1) prevents false positives during field
gameplay, but cannot distinguish "splash screen" from "title screen" because
FIELD_ID is 0 in both cases.

After the spurious splash announce, last_cursor = 0. The real title screen
also starts at cursor = 0, so no second announce fires — user must navigate
once (Up/Down) to hear their position.

Fix ideas:
  - Find a reliable in-process "title screen is actually active" indicator
    (separate from FIELD_ID). Possible candidates: a title-screen state
    variable, a menu-system flag, or the presence of specific title-screen
    assets in memory.
  - Alternatively, delay TitleCursorThread's first poll until after the splash
    duration (e.g., 5s) — crude but effective if splash length is fixed.
  - Document as known limitation until a reliable indicator is found.


[TTS] Quit dialog — speak prompt text on every open
----------------------------------------------------
Currently the "Do you want to quit?" dialog speaks only the cursor position
(Yes/No) when it first appears, with no context for what the dialog is asking.
A blind player who re-opens the dialog after cancelling hears only "No" with no
indication of what question is being answered.

Fix: detect the dialog-open transition and prepend a short spoken prompt, e.g.
"Quit game?" before the cursor position, every time the dialog appears.
Requires a reliable QUIT_OPEN flag — current candidate 0x00DC0FB1 does not
return to 0 after the dialog is cancelled (see ff7_addresses.h). A new scan
comparing "main menu without dialog" → "dialog open" → "dialog dismissed to
main menu" (a 3-way scan, not 2-way like the original) would isolate the flag.


[TTS] Quit dialog — re-announce selected option on every dialog open
---------------------------------------------------------------------
When the Quit dialog is opened a second time (e.g., player pressed No then
opens Quit again), the cursor defaults to No, but QUIT_CURSOR is already at 1
(No) from the last session so last_quit_cursor matches and no announce fires.
Player hears silence and must press Left then Right to hear "No".

Fix: detect dialog re-open (requires QUIT_OPEN flag above, or detect
MENU_CURSOR transitioning to 10 as a proxy) and reset last_quit_cursor to 0xFF
at that moment so the default position is always announced.


[NAV] Wall-slide tone (angled wall contact gives no feedback)
--------------------------------------------------------------
The v2.6 wall-bump tone only fires on a DEAD STOP (direction held, position
frozen). Hitting a wall at an angle stays silent because FF7's walkmesh
redirects the player's FULL velocity along the wall — measured 2026-07-09
(ff7_wall_slide_verify.py): sliding displacement per poll was IDENTICAL to
free walking (median 32765 units/50ms in both; ratio exactly 1.00). So no
displacement-magnitude threshold can ever detect sliding — the engine gives
away no speed.

What WOULD work: compare the COMMANDED direction (current_key_input_status
direction bits) against the ACTUAL motion direction (atan2 of per-poll
displacement). Free movement: they agree. Sliding: they diverge strongly.
Complication: input is camera-relative, world position is world-absolute,
and every field has its own camera orientation — mapping input to expected
world direction needs either the field camera matrix (field file section 2)
or empirical per-field calibration (learn the input→motion mapping while
moving freely, flag sustained divergence as sliding).

Useful measured constants (same session):
  - displacement per 50ms poll = movement_speed * 32 / 20Hz-tick, exactly
    proportional (walk speed=1024 → 32765/poll, run=4096 → 131062/poll)
  - sliding occasionally hard-stops for 1-2 polls (p10 displacement was 0
    in the slide phase) — those moments already trigger the existing
    dead-stop tone, which is why angled contact sometimes chirps.

User decision 2026-07-09: wanted as a DISTINCT tone (higher/softer than the
220 Hz dead-stop tone) so "fully blocked" and "scraping along a wall" are
distinguishable by ear. Deferred until the direction-mismatch approach is
designed.


[TTS] Name entry — side panel (Space/Delete/Select/Default) is silent
----------------------------------------------------------------------
The v2.8 name-entry TTS covers the 7x10 character grid and name readback,
but the right-hand button panel is undetectable: NAME_ENTRY_ROW/COL keep
their last grid values while the cursor is on the panel (confirmed live
2026-07-12 — pressing Right past column 9 changed neither).

Candidate byte 0xDD4574 moved 0->1 at the moment of a Right-past-the-edge
press, but its behavior is inconsistent: it also changed 3->2 once alongside
a character delete, and it did NOT reset when the cursor returned to the
grid. Not usable without more data.

Next step: at the next naturally-occurring naming screen (Tifa in Sector 7,
Aeris at the church, or a New Game restart), run a focused probe: watch
0xDD4560-0xDD45B0 while the player slowly enters/leaves the panel and moves
Up/Down inside it, narrating each press afterwards. Also log 0xDD45E8
(u32: small values while editing, 0xFFFFFFFF at times — possibly related).

Also unresolved from the same session: 0xDD46F0 (8 on Cloud screen with
"CloudGHR", 6 on Barret screen with "Barret" — maybe name length at screen
open; not updated live during editing).


[TTS] Name entry — grid row 5 columns 8-9 unverified
-----------------------------------------------------
kNameGrid guesses apostrophe (col 8) and double-quote (col 9) for row 5;
the reference screenshot was unreadable there. If a player lands on those
cells the spoken guess may be wrong. The add-echo is immune (it decodes the
byte the game wrote), so navigating there and pressing Confirm reveals the
truth — fix kNameGrid in proxy.cpp when observed.


[CONFIG] Auto-create default config file if missing
----------------------------------------------------
If the user places version.dll in the FF7 folder but forgets ffvii_accessibility.cfg,
Config::Load() currently fails silently and the mod runs with all defaults
(which is actually correct behavior). However, there is no config file for the
user to edit to enable/disable features.

Fix: in Config::Load(), after failing to open the file, write a default
ffvii_accessibility.cfg to the same directory with all defaults and a header
comment explaining each option. This gives the user an editable starting point
without requiring them to find documentation.

Implementation note: the DLL knows its own path via GetModuleHandleEx +
GetModuleFileNameA (same pattern used in TTS::Init() to locate Tolk.dll).
