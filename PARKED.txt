[DIALOGNUM] Numbers sometimes not read in dialog (squats minigame)
------------------------------------------------------------------------
Parked: 2026-08-06 (from bug_report.txt; tester update).
"Sometimes it's not reading out numbers during dialog. Noticeable
during squats mini game."
ROOT CAUSE FOUND 2026-08-07 (log.6 squats session 20:30-20:35 + the
user's frame captures): the number is NOT in the text bytes — FF7's
FE DE function code inserts a numeric variable at render time. Squats
results carry it exactly where the screen shows the count ("Here's
the squats you managed <FE DE>." on screen reads "...you managed 6.",
20:32:46; final score "He did <FE DE> many squats, and you did
<FE DE> that many.", 20:33:20). Same mechanism as [INNGIL] — one fix
serves both. v2.30.91 made FE DE an explicitly consumed escape
(behavior unchanged: number still silent, words no longer at risk of
fusing); SPEAKING the value needs the engine's message-variable
source (window numeric params, set by the field script's MPARA
family) — one static session when revived. Note the squats COUNTDOWN
is separate and already tracked (STTIM/WSPCL type=1 armed, TIMER
ticks logged both rounds); the live squat COUNTER during the 30s has
no window at all in the logs — nothing to hook there yet.

[NAV] Wall-slide tone (angled wall contact gives no feedback)
--------------------------------------------------------------
The v2.6 wall-bump tone only fires on a DEAD STOP (direction held, position
frozen). Hitting a wall at an angle stays silent because FF7's walkmesh
redirects the player's FULL velocity along the wall — measured 2026-07-09
(ff7_wall_slide_verify.py): sliding displacement per poll was IDENTICAL to
free walking (median 32765 units/50ms in both; ratio exactly 1.00). So no
displacement-magnitude threshold can ever detect sliding — the engine gives
away no speed.

What WOULD work: compare the COMMANDED direction (current_key_input_status
direction bits) against the ACTUAL motion direction (atan2 of per-poll
displacement). Free movement: they agree. Sliding: they diverge strongly.
Complication: input is camera-relative, world position is world-absolute,
and every field has its own camera orientation — mapping input to expected
world direction needs either the field camera matrix (field file section 2)
or empirical per-field calibration (learn the input→motion mapping while
moving freely, flag sustained divergence as sliding).

Useful measured constants (same session):
  - displacement per 50ms poll = movement_speed * 32 / 20Hz-tick, exactly
    proportional (walk speed=1024 → 32765/poll, run=4096 → 131062/poll)
  - sliding occasionally hard-stops for 1-2 polls (p10 displacement was 0
    in the slide phase) — those moments already trigger the existing
    dead-stop tone, which is why angled contact sometimes chirps.

User decision 2026-07-09: wanted as a DISTINCT tone (higher/softer than the
220 Hz dead-stop tone) so "fully blocked" and "scraping along a wall" are
distinguishable by ear. Deferred until the direction-mismatch approach is
designed.
